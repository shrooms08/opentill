## Where it stopped — it didn't. Two script-side stumbles, no protocol blocker

- `registerVault` requires `nonce` **or** `account: { baseUrl }` (fixed in the script).
- The daemon's Bitcoin RPC proxy (`POST /`) timed out once at 30 s around a block boundary; a rerun resumed from persisted state. Use ≥60 s timeouts against the proxy.
- The doc line "Total elapsed 8208s" under §7 is a unit bug in the first run (it was ~8.2 min); fixed for future runs.

## Findings that matter

1. **A real unilateral exit is achievable on regtest today**, end to end, with the shipped SDK — the sovereignty claim is demonstrable, not theoretical. Wall clock is dominated by regtest's **fixed 10-minute L1 cadence**: faucet → deposit → exit is three blocks ≈ **30 min minimum** with `csvBlocks=1`; with the SDK default **1008-block CSV it is ~7 days**. The daemon accepted a vault registered with `csvBlocks=1` without complaint.
2. **The vault is L1 custody, not ledger credit.** Registering a funded vault does **not** mint a ledger VTXO; the value stays in the L1 funding UTXO under the 2-leaf script. So the vault path and the ledger-VTXO path OpenTill's invoices use are **two separate value pools** — there is no observed bridge from ledger VTXOs (what merchants receive) into a vault (what can exit). That is the real gap for payouts, and it is unchanged by this spike.
3. **The quorum co-signs on request.** `/tachi_signTransaction` returned 5 valid partials for a user-signed refund immediately — the cooperative path is live and fast (seconds). Its output is a `to_local` commitment; claiming it to a plain address is a further CSV-gated, user-only spend (not attempted; same mechanics as the exit).
4. **The daemon does not react to an on-chain exit.** After the exit confirmed, `listVaults` still reports vault A `open`; the watchtower (`mode: detection`, scanned the exit's block) recorded 0 receipts — correct, since an exit-leaf spend is not a breach — but the vault record never closes.

## Precise questions for the Tachi team

1. **Is there, or will there be, a ledger → vault bridge?** A merchant's receipts are plain-key ledger VTXOs; the only demonstrated L1 exit is from a vault funded **from L1**. Can ledger VTXOs be moved into a vault's funding output (or otherwise redeemed to L1) without an L1 deposit? This is the single blocker between OpenTill's receipts and a real payout.
2. Should an observed exit-leaf spend transition the vault to a closed state on the ledger (currently stays `open`), and is there a `TxVaultClose` a client should send?
3. What CSV value do you consider safe on signet/mainnet, given a 1-block CSV was accepted on regtest?

## Verdict: wire it in, or keep payouts simulated?

**Keep payouts simulated in the product for now — but ship this spike as the proof.** The exit and the cooperative refund are real and reproducible (`npm run spike:vault`), which is exactly the video moment and the honest counter to "it's all mock." What is *not* real is the connection to money OpenTill actually holds: invoice receipts live as ledger VTXOs, and nothing observed today moves them into a vault. Wiring the vault flow into `initiatePayout` would therefore let a merchant exit *only* funds they first deposited from L1 — a demo of the mechanism, not a payout of their sales. The honest product statement stays: receiving, confirmation and refunds are real; payouts await answer #1. The moment Tachi provides a ledger→vault (or ledger→L1) bridge, the adapter's `initiatePayout` is a ~1-day job on top of this script.
