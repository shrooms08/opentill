```
  decode.type=transfer
  broadcast: code=3 log="invalid signature"

C3 WITHDRAW (type 5), bogus sig, transfer shape — Tachi: 'validated exactly like a transfer'
  decode.type=withdraw
  broadcast: code=3 log="invalid signature"

C4 LOCK (type 6), bogus sig, transfer shape + finalized PSBT — same as W2 but bogus sig
  decode.type=lock
  broadcast: code=3 log="invalid signature"

C5 LOCK (type 6), bogus sig, outputs=[] + finalized PSBT
  decode.type=lock
  broadcast: code=12 log="invalid transaction format"

C6 type 7 (unlock?), bogus sig, transfer shape
  decode.type=unlock
  broadcast: code=3 log="invalid signature"

C7 type 2 (unknown), bogus sig, transfer shape — control for an undefined type
  decode.type=unknown
  broadcast: code=12 log="invalid transaction format"
```

**Reading:** `code 12 invalid transaction format` is reused by two different checks. (1) The *generic* format check runs before signature verification and rejects **empty `Outputs`** (C5) and unknown types (C7) — so `Outputs` must be non-empty (answering the open question). (2) With non-empty outputs the lock shape *passes* the generic check (C4 → `invalid signature`), yet the identical shape with a **valid** signature (W2) still gets `code 12` — a **lock-specific validation after signature verification** is failing and reports the same code. Types 5 (`withdraw`) and 7 (`unlock`) pass the generic check with the plain transfer shape.

## What the daemon actually accepts — the `Outputs` question, answered

The bogus-signature probe (§3c) separates the checks because a shape that passes the format layer fails later with `code 3 invalid signature` instead of `code 12`:

- **`Outputs` must be non-empty.** With `outputs=[]` a `lock` is rejected `code 12` *before* signature verification (C5) — the generic format check, exactly as Tachi suspected. A zero-value placeholder output also does not help (V4).
- **With non-empty outputs the lock envelope passes the generic format check** (C4 → `invalid signature`). So the SDK transfer wire layout is fine for type `0x06`, and `/tachi_txDecode` parses it as `type: "lock"` with correct vin/vout.
- **But with a valid signature the same shape is rejected `code 12` again** (W2, X2 …) — a **lock-specific validation that runs after signature verification reuses the format error code**. Nothing we can vary from the documented contract changes it: PSBT unfinalized / genuinely finalized (real input with `finalScriptWitness`, exactly one P2TR output paying the vault's own address) / absent; PSBT output value 50 000 (= VTXO), 49 999, 49 500; ledger output to the owner or to the vault's taproot key; ledger fee 1 or 0; input `txid` zero, funding txid in internal or display order.
- **`/tachi_txValidate` is unusable as evidence**: it fails *valid, routinely-committed* transfers with `input 0 sigscript: need 16705 bytes` (L5 control) — a decoder bug in that endpoint.
- Side findings: types `5` (`withdraw`) and `7` (decodes as `unlock`) pass the generic format check with the plain transfer shape; type `2` does not.

## Where it stopped and why

At stage 3, on a **post-signature, lock-specific rule the daemon does not name**. The contract as relayed ("finalized PSBT with exactly one P2TR output; referenced VTXO exists and is not locked; only a fee-balance check") was satisfied by several variants (W2/X2 in particular), so at least one undocumented requirement remains — candidates: the PSBT must spend something specific (the receipt's backing? the vault's funding via the *cooperative* leaf, which needs quorum signatures we cannot obtain for a lock?), the output must carry a particular script, or the daemon derives the vault address differently from a user-signed exit-leaf PSBT. From outside, `code 12` is the only signal.

## Is `initiatePayout` implementable for real now?

**No — not yet, and the block is narrower than before.** The vault-side machinery (cooperative refund with 5-of-7 quorum signatures, unilateral exit) is proven; the plain ledger paths (receive, transfer, refund) are proven; `TxLockForVault` is the single missing link and it fails on an unnamed rule. What it would take, in order:

1. **From Tachi:** the exact post-signature validation rules for `0x06` — ideally a Go-side builder or a byte-exact payload example that commits on regtest — and a distinct error code/log for that check (`code 12` is currently ambiguous).
2. **Then, the product-relevant cooperative path** is straightforward on top of what already runs: receipt VTXO → `TxLockForVault` → `buildRefundPsbt` → `/tachi_signTransaction` (proven, seconds) → finalize → L1 broadcast; unilateral exit stays the sovereignty backstop. Roughly a day once (1) lands, because every other step exists in `scripts/tachi-vault-spike.ts` and the adapter.
3. **One open semantic question even after the lock works:** the L1 value that leaves a vault is its **funding UTXO** (what we deposited), so what backs the L1 payout of a *locked receipt* — must the vault's own L1 funding cover the locked amount (merchant pre-funds their own exits), or does the quorum-cosigned refund draw on network liquidity? This decides whether payouts of sales are real without the merchant first parking L1 collateral.

## Questions for the Tachi team

1. What does `TxLockForVault` validation check *after* the signature, and can it return a distinct code/log? A byte-exact regtest example (or the Go builder) would settle it.
2. Must the PSBT payload spend the vault's funding via the **cooperative** leaf (i.e., does a lock require quorum signatures inside the PSBT), or is a user-signed exit-leaf self-spend acceptable? Must its single output value equal the VTXO amount?
3. After a successful lock, what backs the L1 payout of the locked amount — the vault's own funding UTXO or network liquidity? (Decides whether sales → payout is real without merchant-supplied L1 collateral.)
4. `/tachi_txValidate` rejects valid transfers with `input 0 sigscript: need 16705 bytes` — decoder bug on that endpoint.
